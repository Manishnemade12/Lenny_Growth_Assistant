# AI Assistant Rules & Conventions

## The Lenny Growth Assistant — Development Guidelines

> These rules govern how AI coding assistants should work on this project. Follow them strictly to maintain consistency, quality, and alignment with the assignment requirements.

---

## 1. Project Context

This is a **Forward Deployed Engineer take-home assignment**. The evaluator will:
- Clone the repo and run it using only the README instructions
- Evaluate code quality, architecture, and completeness
- Test all features against the PRD acceptance criteria
- Review documentation for clarity and thoroughness

**CRITICAL**: Every decision must optimize for **evaluator experience**. If something works but is hard to understand, it's a failure.

## 2. Architecture Rules

### 2.1 Backend (Python / FastAPI)

- **Framework**: FastAPI with async/await everywhere. No sync database calls.
- **Python version**: 3.11+ (use modern syntax: `list[str]` not `List[str]`, `str | None` not `Optional[str]`)
- **Database ORM**: SQLAlchemy 2.0+ async with `asyncpg` driver
- **Migrations**: Alembic. Always create migrations for schema changes. Never use `create_all()` in production.
- **Schema validation**: Pydantic v2 for all request/response models. Never pass raw dicts to/from APIs.
- **Agent SDK**: Use Anthropic Claude Agent SDK (`claude-agent-sdk`) or implement your own agent loop with the Anthropic Python SDK
- **Dependency injection**: Use FastAPI's `Depends()` for DB sessions, services, and providers
- **Error handling**: Global exception handler. All errors return `{ "error": str, "code": str, "detail": str|null, "timestamp": str }`

### 2.2 Frontend (React / TypeScript)

- **Framework**: Vite + React 18+ + TypeScript (strict mode)
- **State management**: Zustand for global state. React Query (TanStack Query) for server state.
- **Styling**: Vanilla CSS with CSS variables. NO Tailwind CSS unless explicitly requested.
- **No component libraries**: Build components from scratch. No MUI, Chakra, Ant Design, shadcn/ui.
- **SSE streaming**: Use native `EventSource` API or `fetch` with `ReadableStream`. No socket.io.
- **Sanitization**: DOMPurify for all HTML artifact rendering. No `dangerouslySetInnerHTML` without sanitization.

### 2.3 Database (PostgreSQL)

- **Version**: PostgreSQL 16+ with pgvector extension
- **Primary keys**: UUID v4, generated by database (`gen_random_uuid()`)
- **Timestamps**: `TIMESTAMP WITH TIME ZONE`, always UTC
- **JSON fields**: JSONB type for metadata, citations, etc.
- **Indexes**: Create indexes on foreign keys and frequently queried columns
- **Naming**: Snake_case for tables and columns

### 2.4 Docker

- **Compose file**: `docker-compose.yml` (v3.8+)
- **PostgreSQL image**: `pgvector/pgvector:pg16` (includes pgvector pre-installed)
- **Backend image**: Multi-stage build from `python:3.11-slim`
- **Frontend image**: Multi-stage build from `node:18-alpine`
- **Volumes**: Named volume for PostgreSQL data persistence

## 3. Code Conventions

### 3.1 Python Code Style

```python
# ✅ DO: Use type hints everywhere
async def create_session(title: str = "New Chat") -> SessionResponse:
    ...

# ❌ DON'T: Omit type hints
async def create_session(title="New Chat"):
    ...

# ✅ DO: Use Pydantic models for API contracts
class ChatRequest(BaseModel):
    session_id: UUID
    message: str = Field(..., min_length=1, max_length=10000)

# ❌ DON'T: Use raw dicts
@router.post("/chat")
async def chat(data: dict):  # NO!
    ...

# ✅ DO: Use structured logging
logger.info("Skill executed", extra={"skill": name, "latency_ms": elapsed})

# ❌ DON'T: Use print statements or unstructured logs
print(f"Skill {name} took {elapsed}ms")  # NO!

# ✅ DO: Handle errors with specific exceptions
except httpx.ConnectError:
    raise ConnectionError(f"Cannot connect to Ollama at {base_url}")

# ❌ DON'T: Use bare except
except:  # NO!
    pass
```

### 3.2 TypeScript Code Style

```typescript
// ✅ DO: Use explicit types for props and state
interface MessageBubbleProps {
  message: ChatMessage;
  isStreaming: boolean;
  onCreateArtifact: (messageId: string) => void;
}

// ❌ DON'T: Use `any`
const MessageBubble = ({ message }: any) => { ... }  // NO!

// ✅ DO: Use enum/union types for states
type LLMProvider = 'ollama' | 'anthropic' | 'openai';
type MessageRole = 'user' | 'assistant' | 'system';

// ✅ DO: Handle loading, error, and empty states
if (isLoading) return <Spinner />;
if (error) return <ErrorMessage error={error} />;
if (messages.length === 0) return <WelcomeScreen />;

// ❌ DON'T: Ignore error states
return <div>{data?.messages?.map(...)}</div>  // NO! What if data is null?
```

### 3.3 CSS Conventions


## 4. File Organization Rules

### 4.1 Backend File Rules

| Rule | Description |
| ---- | ----------- |
| **One router per domain** | `chat.py`, `sessions.py`, `artifacts.py`, `config.py`, `health.py` |
| **Repository pattern** | All DB queries go through repository classes, never in route handlers |
| **Schema per domain** | Separate Pydantic schema files matching route files |
| **Skills are self-contained** | Each skill has its own system prompt, intent detection, and execution logic |
| **Providers implement interface** | Every LLM provider implements `BaseLLMProvider` abstract class |
| **Config is centralized** | All settings in `app/config.py`, loaded from environment |

### 4.2 Frontend File Rules

| Rule | Description |
| ---- | ----------- |
| **Feature-based folders** | Components grouped by feature: `Chat/`, `Sidebar/`, `Artifacts/`, `common/` |
| **One component per file** | Each `.tsx` file exports one component |
| **Hooks for logic** | Business logic in custom hooks (`useChat`, `useSessions`, `useArtifacts`) |
| **Services for API** | All API calls in `services/` directory |
| **Types in `types/`** | Shared TypeScript interfaces in dedicated type files |
| **Styles collocated** | CSS files next to their components OR in central `styles/` |

## 5. Assignment-Specific Rules

### 5.1 Mandatory Requirements (Must Have)

These are non-negotiable requirements from the assignment. Do not skip any:

- [ ] **FastAPI backend** — Not Flask, not Django
- [ ] **PostgreSQL with persistence** — Not SQLite, not in-memory
- [ ] **Ollama for local demo** — Must work with Ollama out of the box
- [ ] **Cloud LLM integration** — At least one of Anthropic Claude or OpenAI
- [ ] **Session management** — Independent sessions with persistence
- [ ] **Grounded answers** — RAG with source citations, not hallucinated
- [ ] **Ship 30 for 30 skill** — Structured skill, not a one-off prompt
- [ ] **Artifact viewer** — In-app rendering, not opening a new tab
- [ ] **Artifact sandboxing** — Documented security strategy
- [ ] **Docker Compose** — One-command startup
- [ ] **`.env.example`** — Never commit real secrets
- [ ] **Structured logs** — JSON format, categorized
- [ ] **Graceful error handling** — For all failure scenarios
- [ ] **Health endpoint** — Aggregated system status
- [ ] **Tests** — Automated + manual test plan

### 5.2 Evaluation Criteria Alignment

When making any implementation decision, score it against these criteria:

| Criterion | Weight | What the Evaluator Looks For |
| --------- | ------ | ----------------------------- |
| **Customer & Product Judgment** | High | PRD quality, assumptions, metrics, trade-offs |
| **Technical Execution** | High | End-to-end functionality, no broken flows |
| **Agentic Architecture** | High | Skill boundaries, routing, grounding, failure behavior |
| **Deployment & Operability** | High | Reproducibility, observability, resilience, docs |
| **Code Quality** | Medium | Clean separation, readability, validation, tests |
| **UI/UX Quality** | Medium | Polished chat, states, artifact viewer, responsive |
| **Communication** | Medium | Clear docs, demo, rationale |

### 5.3 Things to Avoid

- ❌ **Committing `.env` files** — Use `.env.example` only
- ❌ **Hardcoding API keys** — Always use environment variables
- ❌ **Using `print()` for logging** — Use `structlog` or Python `logging` with JSON formatter
- ❌ **Skipping error handling** — Every API call, DB query, and LLM call needs try/catch
- ❌ **Monolithic files** — No 500+ line files. Split by responsibility.
- ❌ **One-off prompts for Ship 30** — Must be a structured, encoded skill
- ❌ **`dangerouslySetInnerHTML` without DOMPurify** — Always sanitize
- ❌ **Blocking calls in async context** — No `requests.get()` in FastAPI, use `httpx`
- ❌ **Missing type hints** — Every function parameter and return type must be annotated
- ❌ **TODO/FIXME comments** — Fix them before submission, or document as known limitations
- ❌ **Copy-pasting large prompts as strings** — Use constants or external files

## 8. Security Rules

1. **Never log secrets**: API keys, passwords, tokens must never appear in logs
2. **Never commit secrets**: Use `.env` files (gitignored) and `.env.example` (committed)
3. **Sanitize all HTML**: Use DOMPurify before rendering any generated HTML
4. **Sandbox iframes**: Always use `sandbox` attribute on artifact iframes
5. **Validate all inputs**: Pydantic models on every API endpoint
6. **Parameterized queries**: Always use SQLAlchemy ORM (no raw SQL string concatenation)
7. **Rate limit awareness**: Document rate limits for cloud LLM providers
8. **CORS properly**: Only allow configured origins, not `*` in production

---

## 9. Testing Rules

1. **Every API endpoint** must have at least one happy-path test
2. **Every skill** must have intent detection tests (true positives and true negatives)
3. **Chunker** must have tests for edge cases (empty text, very long text, single word)
4. **Provider fallback** must have a test showing graceful degradation
5. **Frontend components** must render without errors in test environment
6. **Use mocks** for LLM providers in tests (don't call real APIs in CI)
7. **Test fixture data** should be committed in `tests/fixtures/`
